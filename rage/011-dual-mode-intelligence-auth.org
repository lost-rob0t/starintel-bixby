Current endpoint guidance supports local endpoints using OAuth and =authorization-error= for invalid/revoked credentials. - Privacy consequence :: local JS must accept only the minimum context necessary to detect authenticated state; raw =$vivContext= must never be copied into the StarIntel request body. Samsung/Bixby identity is not StarIntel identity.
- Provider blocker :: =starintel-server#111= still owns canonical authorize/token endpoints, Bixby client registration, redirect validation, PKCE/lifecycle, and StarIntel human-principal semantics. Do not fabricate =authorization.bxb= URLs before that exists.

** Design
- Keep the existing local JS adapters and public =/v1/bixby/person/resolve= / =/v1/bixby/documents/search= contract family.
- Change endpoint declarations to optional user OAuth only when a real provider declaration is available; until then, model/test the dual-path local JS behavior without inventing provider URLs.
- Local actions accept =$vivContext= only to inspect whether an access token exists. They never forward =$vivContext=, =bixbyUserId=, locale, device, location, Samsung profile, or token text in request JSON.
- Guest request :: ordinary =http.postUrl= through the configured public gateway origin.
- Signed-in request :: =http.oauthPostUrl= so Bixby attaches the managed OAuth credential; token material is not manually copied into headers/body/query by capsule code.
- Invalid/expired/revoked signed-in request :: authorization failure must propagate as Bixby =authorization-error= rather than silently retrying anonymously when the authenticated path was selected.
- Both paths use identical narrow request builders and response normalizers, preserving result bounds and mutation exclusion.

** Threat model / adversarial review
- Silent auth downgrade :: reject; a failed signed-in request cannot be retried as guest because that could hide authorization failure and return a misleading public subset.
- Token/body/header leakage :: reject manual token plumbing; prefer Bixby's OAuth HTTP methods.
- Ambient context leakage :: only check presence of =$vivContext.accessToken=; do not serialize or forward the context object.
- Identity confusion :: never use =$vivContext.bixbyUserId= or Samsung account fields as a StarIntel principal.
- Scope confusion :: Intelligence remains read/search only; no target, Auto-Dig, ingest, or admin authority.
- Caller scope widening :: tenant/dataset authority remains server-owned and absent from capsule request builders.
- Cross-user/cache leakage :: owning gateway/server must key authenticated responses by authenticated principal and avoid shared caching of token-bearing private responses; frozen contract issue #8 must preserve this.
